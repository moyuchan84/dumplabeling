「다시 묶기」는 무엇을 어떻게 묶나

다시 묶기를 누른 순간부터, 기록 목록에서 기록을 눌러 묶음 지도에 그 자리가 뜨기까지의 실제 코드 흐름입니다. 2026-10-28 변경(묶음 범위에 sensor_id 추가, 면 스캔을 X · Z 단면과 칸으로 따로 정규화) 반영본이며, 2026-10-30 변경(범위에 chuck_id 추가 · 잣대를 채널 간 편차로)은 바로 아래 상자에 적었습니다.

한눈에

기간 조건은 없다

scanlabel 이 지금까지 본 기록 전부(기록 풀)가 재료입니다. 날짜로 자르지 않고, 범위마다 최근에 바뀐 800건까지만 씁니다.

fleet 은 부르지 않는다

다시 묶기는 풀에 저장된 특징 스냅샷만 읽습니다. FTP·fleet 호출이 없습니다.

범위 = 스캔 종류 × 척 × 센서

scan_enum 이 같아도 chuck_id 나 sensor_id 가 다르면 따로 묶고 따로 지도를 그립니다(2026-10-30 에 척 추가, SL-CLU-3).

잣대 = 채널 간 편차 (2026-10-30)

묶음 · 지도의 점수는 한 채널의 모양이 아니라 같은 자리에서 채널(tr · txh · tyh …)끼리 어긋난 정도입니다. 채널마다 제 평균 · 표준편차로 잰 값에서 채널 평균을 빼고, 그 범위가 평소 어긋나는 만큼(자리마다 중앙값)을 다시 뺀 뒤, 남은 어긋남의 자리 · 방향 · 크기를 비교합니다(SL-CLU-9). 아래 흐름에서 「유사도」는 이 점수로 읽습니다. 라벨 제안은 그대로 모양 유사도입니다.

묶음 = 대표와 0.8 이상

구성원 모두가 대표 기록과 직접 0.8 이상 닮아야 하고, 3건 미만이면 묶음이 아닙니다.

  2. 재료 읽기 — Store.pool(): scan_records 에서 set_name='dump' 행을 (scan_enum, chuck_id, sensor_id) 로 나누고, 범위마다 seq(특징이 마지막으로 쓰인 순서) 내림차순 800건. 넘친 수는 truncated 로 남깁니다.

언제 · 어떤 데이터

행 하나는 (servername, set, 파일, source) 기록 하나이고, 특징 스냅샷과 메타 사본(scan_enum · chuck_id · sensor_id · 시각)을 가집니다. 같은 세대·같은 특징 판·같은 범위면 다시 열어도 행이 바뀌지 않습니다. 그래서 같은 파일을 다시 열어도 「새 기록 있음」이 뜨지 않습니다.

특징 스냅샷 (채널마다)

  • 측정 순서 곡선 — 스캔 순서 배열을 128점으로 줄인 것(구간 평균, 짧으면 선형 보간). 선 스캔만 비교에 씁니다
  • 칸 — (x, z) 평면을 16×16 칸으로 나눈 칸 평균(빈 칸은 비움). 점들이 한 줄 위에 있으면 칸 없음(선 스캔)
  • n · min · max · mean · std — 정규화 전 값 그대로

3. 두 기록이 얼마나 닮았나 (점수)

shape.similarity
  1. 채널마다 비교 재료를 고릅니다. 면 스캔(칸이 있음 — 지금 풀의 기록 전부): X 단면(칸의 열 평균, 16점) · Z 단면(행 평균, 16점) · 칸(16×16). 선 스캔: 측정 순서 곡선(128점). 면과 선은 비교하지 않습니다.
  2. 재료마다 따로 z-score 로 정규화합니다. 오프셋과 배율이 사라지므로 크기가 아니라 모양만 남고, 한 방향의 큰 기울기가 다른 방향의 모양을 묻지 않습니다.
  3. 1D = X 단면 상관과 Z 단면 상관의 평균(각각 공통 자리 8개 이상), 2D = 칸 상관(공통 칸 16개 이상). 선 스캔은 1D = 곡선 상관.
  4. 채널 점수 = 1D 0.5 + 2D 0.5(있는 쪽만). 기록 점수 = 두 기록에 다 있는 채널의 평균. 공통 채널이 없으면 비교하지 않습니다.
  5. 평평한 채널은 상관을 내지 않습니다. 평평 대 평평 = 1, 평평 대 그 외 = 0.

4. 어떻게 묶나 — 대표 기록 묶음

shape.cluster
  1. 범위 안 모든 쌍의 점수를 내고, 0.8(CLUSTER_MIN) 이상인 짝을 이웃으로 적습니다.
  2. 남은 기록 중 이웃이 가장 많은 것을 대표로 고릅니다(동점이면 이웃 점수 합, 그다음 id).
  3. 대표 + 그 대표의 남은 이웃을 한 묶음으로 떼어 냅니다.
  4. 대표의 남은 이웃까지 3건(CLUSTER_MIN_SIZE) 미만이 될 때까지 반복합니다. 남은 것은 「묶이지 않음」입니다.
  5. 묶음 번호는 큰 묶음부터 1, 2, 3…

사슬 묶기(A~B, B~C 이면 A·C 도 같이)는 쓰지 않습니다. 모양이 전혀 다른 A 와 C 가 B 를 거쳐 한 묶음이 되기 때문입니다.

묶음의 분류(카테고리)

라벨된 구성원의 라벨을 단계(대·중·소)별로 셉니다. 소분류 라벨은 그 중분류·대분류의 표이기도 합니다. 한 단계의 1위가 라벨된 구성원의 60% 이상이고, 2위보다 많고, 바로 위 단계 합의 노드의 자식이면 그 단계는 「합의」입니다. 합의된 가장 깊은 단계가 묶음의 분류이고, 라벨된 구성원이 없으면 분류도 없습니다.

묶음 지도(2D)

범위마다 서로 가장 먼 기록 24개를 기준점으로 골라(거리 = 1 − 점수) 고전 MDS 로 2D 에 놓고, 나머지는 기준점까지의 거리만으로 투영합니다. 근사라서 가까우면 대체로 닮았지만 거리가 정확하지는 않습니다. 투영식을 저장해 두므로 묶은 뒤에 본 기록도 다시 묶지 않고 지도에 놓을 수 있습니다.

5. 기록을 누르면 지도에 어떻게 뜨나

GET /clusters/map

Dump 화면에서 기록을 고르면 사례 패널이 그 기록을 target = (server_id, file, source) 로 묶음 탭에 넘깁니다. 지도는 이 순서로 정해집니다.

  1. scanlabel 이 그 기록을 풀에서 찾습니다. 풀에 없으면 fleet 캐시에서 읽어 특징만 계산합니다.
  2. 지도 범위 = 사람이 콤보박스로 고른 범위, 없으면 그 기록의 (스캔 종류, 척, 센서), 기록도 없으면 가장 큰 범위.
  3. 보이는 범위가 기록의 범위와 같을 때만 「지금 기록」 표시를 그립니다.

6. 아래 영역이 누를 때마다 바뀌는 이유

라벨 있음 · 라벨된 구성원 없음

지도 아래 영역은 하나의 상태(view)로 셋 중 하나를 그립니다. 지도를 누를 때마다 이 상태가 바뀌므로 그래프와 문구가 함께 바뀝니다. 지도 자체는 다시 불러오지 않습니다.

누른 것아래에 그려지는 것보이는 라벨 문구의 조건
처음 · 「← 묶음 목록」 · 다시 묶기묶음 목록 — 행마다 대표의 X · Z 단면 · 분류 · n건 · 라벨 k분류가 없으면 옅게 이유: 라벨된 구성원 없음 / 합의 없음
지도의 점기록 상세 — 그 기록의 라벨 · 묶음 · 지금 기록과의 점수 · 두 기록의 X · Z 단면(지금 기록 잉크, 누른 기록 강조색, 단면마다 따로 그림)과 칸 그림 두 장그 기록에 라벨이 있으면 라벨 경로, 없으면 「라벨 없음」
지도의 #번호 · 「그 묶음 보기」 · 목록의 행묶음 하나 — 대표 + 구성원의 X · Z 단면 · 단계별 분류 · 라벨 붙이기 · 구성원 목록라벨된 구성원이 0명이면 「라벨된 구성원이 없습니다」, 모두 라벨이 있으면 「구성원 모두 라벨이 있습니다」

지도의 점 모양

  • ● 채운 점 = 그 기록에 라벨이 있음 (scan_labels 에 행이 있음)
  • ○ 빈 점 = 라벨 없음
  • 옅은 점 = 묶이지 않은 기록 · 선 = 묶음 경계(볼록 껍질) · 강조색 고리와 십자 = 지금 기록

라벨을 붙이거나 다시 묶으면 숫자와 ●/○ 가 바뀝니다. 라벨 여부는 다시 묶지 않아도 즉시 반영되고, 묶음 구성은 다시 묶어야 바뀝니다.

7. 다시 묶어도 묶이지 않는 경우

기록이 아직 풀에 없었다

그 파일을 연 적이 없고 jobs index 도 돌지 않았으면 재료에 없습니다. 파일을 연 뒤 「새 기록 있음」이 뜨면 다시 묶어야 들어갑니다.

범위 안 기록이 너무 적다

범위가 3건 미만이면 묶음도 지도도 없습니다. 센서까지 나눈 이번 변경으로 범위가 작아지므로 이 경우가 늘 수 있습니다.

닮은 기록이 모자라다

대표와 0.8 이상인 기록이 2건 이상 모여야 합니다. 공통 채널이 없거나 채널이 평평하면 점수가 없거나 0입니다.

800건 상한

범위마다 최근에 바뀐 800건만 묶습니다. 오래된 기록은 지도에 투영만 됩니다.

작업 실패 · 상태 유실

실패하면 탭에 빨간 문장과 이유가 나오고 목록은 이전 결과입니다. 작업 상태는 API 프로세스 메모리에만 있어서, 묶는 도중 scanlabel 이 재시작되면 결과 없이 상태가 사라지고, CLI jobs cluster 의 진행은 화면에 보이지 않습니다(결과만 보임).
