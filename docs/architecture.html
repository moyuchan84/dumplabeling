scanlabel 아키텍처 & 호출 흐름

dump 스캔 기록 하나하나에 대 › 중 › 소분류 라벨을 붙이고, 화면에 띄운 기록과 모양이 닮은 라벨된 기록을 찾아 라벨을 제안하고, 라벨 없는 기록까지 모양으로 묶어(클러스터) 묶음 단위로 분류하게 해 주는 서비스입니다. ftpmodule(fleet)·poc_viewer 와 어떻게 맞물려 돌아가는지 정리했습니다.

poc_viewer — 입력 · 표시 (Next.js) ftpmodule(fleet) — 수집 · 해석 · 서빙 scanlabel — 라벨 · 유사도 · 묶음 판단 기준 커밋 68e1a7e · 테스트 58개 통과

01한눈에 보기

세 프로젝트는 역할이 겹치지 않게 나뉘어 있습니다. 가져와서 해석하는 일은 fleet, 판단하는 일은 scanlabel, 입력받고 보여 주는 일은 poc_viewer 입니다.

ftpmodule (fleet)

수집 · 파싱 · 서빙 — Python / FastAPI :8000
  • 장비 FTP 를 스윕해 파일을 미리 받아 해석(name@sig 세대 단위)
  • 해석 결과를 PG(TimescaleDB)에 저장, HTTP 로 서빙
  • 사례(/cases)·분석(/analyses)의 소유자
  • scanlabel 을 모른다 — 알 필요도 없다

scanlabel

라벨 · 유사도 · 묶음 판단 — Python / FastAPI :8100
  • 라벨 트리(3단계 고정)와 기록 라벨 저장
  • 스캔 곡선 → 특징 → 상관 유사도 → 단계별 제안
  • 기록 풀을 모양으로 묶고, 묶음의 분류·2D 지도 계산
  • fleet 은 공개 HTTP · 캐시 전용으로만 읽는다

poc_viewer

입력 · 표시 — Next.js 16 / React 19 :3000
  • Dump 화면의 「사례」 패널: 이 기록 라벨 · 묶음 탭
  • 같은 출처 /api/fleet/*, /api/scanlabel/* 로 두 서비스를 부른다
  • 판단하지 않는다 — 점수·문턱·합의 여부는 서버 값을 옮겨 적기만
  • scanlabel 이 죽어도 화면은 죽지 않는다
핵심 설계 한 줄 「ftpmodule 은 데이터를 가져와서 parsing 하는 거 위주였는데 … 별도의 project 를 분기해서」 — 분석(특징·유사도·분류·묶음)은 수집 서비스 안에 넣지 않고 따로 뗐습니다 (SL-ROLE-2, SL-X-1). 그래서 scanlabel 은 fleet 의 DB 를 읽지도, 코드를 import 하지도 않으며, fleet 은 scanlabel 의 존재를 모릅니다 (SL-FLEET-1).

06판단 로직 (processing/shape.py)

"비슷한 모양은 같은 원인을 공유한다"는 가설 위에서, 학습 없이 최근접 비교로 동작합니다. 모든 문턱값·가중치는 이 파일의 상수 한 곳에만 있습니다 (SL-SUG-4).

6.1 파이프라인

① 레코드 짝짓기구조로 구분: xyz+value = raw, results = meta, meta.pair = raw.sourceconnectors/fleet.pair_scans
② 특징 스냅샷채널마다 128점 경로 + 16×16 격자 + 통계(정규화 전 값)record_features · FEATURE_VERSION=1
③ 유사도z-score 후 피어슨 상관 — 1D·2D 가중 평균, 크기비는 따로similarity · prepare
④ 단계별 투표라벨은 자기 노드+조상에 투표 → 대/중/소 각 단계 "확실" 판정rank
⑤ 사례·묶음·지도닮은 기록이 가리키는 사례, 대표 시드 묶기, landmark MDSsimilar_cases · cluster · cluster_map

6.2 특징 스냅샷과 유사도

특징 (정규화 전 값을 저장)

  • 채널마다 스캔 순서 배열을 PATH_N = 128점으로 축소(구간 평균, 짧으면 선형보간)
  • (x, z) 평면을 min–max 로 맞춰 16×16 셀 평균 (빈 셀 = null)
  • n · min · max · mean · std
  • 채널은 value 키로만 맞춤 — 검출기→채널 규칙을 복사하지 않음
  • ""/null/NaN 은 버림 (0 으로 읽지 않음)
  • 점이 직선·한 점이면 2D 특징 없음

정규화 전 값을 저장하므로 정규화 방식만 바꿀 땐 원본이 필요 없습니다. 스냅샷 모양이 바뀌면 FEATURE_VERSION ↑ → jobs refeature.

유사도 규칙

채널 점수 = 0.5 · corr1D + 0.5 · corr2D   (있는 쪽만)
기록 점수 = 공통 채널 점수의 평균
corr = z-score(offset·gain 제거) 후 피어슨
  • 1D 는 같은 궤적끼리만 — 행 수가 다른 래스터는 인덱스 순서가 달라 무의미. 그래서 기본 비교 범위 = 같은 scan_enum
  • 2D 는 두 쪽 모두 값이 있는 셀 ≥ MIN_OVERLAP(16)
  • 평평한 신호끼리 = 1, 평평 vs 그 외 = 0 (노이즈를 모양으로 키우지 않음)
  • 크기 정보는 정규화로 사라지므로 scale 비를 점수에 섞지 않고 따로 반환
  • 공통 채널이 없으면 비교 안 함 · 자기 자신은 제외

6.3 단계별 제안 — "확실"은 서버가 정한다

  • 라벨된 각 후보 기록은 자기 노드와 모든 조상에 투표 (소분류 라벨 = 중·대분류 표도 됨)
  • 노드 점수 = 그 아래 기록들의 최고 점수, 근거 건수 = 점수 ≥ 0.60 인 기록 수
  • 한 단계가 확실 ⇔ 1위 ≥ 0.80 이고, 2위보다 0.05 이상 앞서고, (대분류가 아니면) 위 단계 확실 노드의 자식
  • 제안 = 확실한 가장 깊은 단계. 문턱 미만이면 아무것도 제안하지 않음 (억지 제안은 근거처럼 읽히므로)
  • 「대분류는 확실, 소분류는 갈림」 같은 부분 확실을 그대로 말할 수 있음
상수값의미
SUGGEST_MIN0.80제안 최소 점수
MARGIN0.052위와의 최소 격차
EVIDENCE_MIN0.60근거 건수 · 사례 투표 최소 점수
LEVEL_TOP · CASE_TOP5 · 5단계별/사례 목록 길이
W_1D · W_2D0.5 · 0.5채널 점수 가중

유사 사례는 같은 점수 ≥ 0.60 기록들이 자기 라벨의 case_id(자기 것, 없으면 가장 가까운 조상 것)로 투표한 결과를 사례 단위로 모은 것입니다.

6.4 묶음(클러스터) — 대표 시드 방식

  1. 같은 스캔 종류 안에서만, 종류당 최근 800건까지 모든 쌍을 비교
  2. 점수 ≥ CLUSTER_MIN(0.80) 이웃이 가장 많은 기록 = 대표
  3. 대표와 남은 이웃들이 한 묶음 → 반복 (동률은 이웃 점수 합 → id 로 결정적)
  4. 3건 미만 무리는 「묶이지 않음」

모든 구성원이 대표와 직접 0.8 이상 닮으므로 A~B~C 로 사슬처럼 이어 서로 안 닮은 모양을 묶는 일이 없습니다 (단일 연결 기각, SL-X-9). 대표 곡선 하나로 묶음을 보여 줄 수 있는 이유이기도 합니다.

묶음의 분류(category) 합의

라벨된 구성원의 라벨을 단계별로 세어(조상 포함) 한 단계가 합의되려면:

  • 1위 노드 비중 ≥ CLUSTER_AGREE 0.60
  • 2위보다 많고, 위 단계 합의 노드의 자식

분류 = 합의된 가장 깊은 단계, 없으면 null(라벨 구성원이 없거나 갈림). 화면은 이유를 "라벨된 구성원 없음 / 한 노드에 모이지 않음"으로 옮겨 적습니다.

6.5 2D 묶음 지도 — landmark MDS

  • 거리 = 1 − score. 기준점 24개를 max–min 으로 고른다
  • 기준점끼리 고전 MDS 로 2D 좌표를 계산
  • 나머지는 기준점 24개와의 거리만으로 투영 (기록당 비교 24회)
  • 투영식(기준점 id · 의사역행렬 · 평균)을 cluster_runs.maps 에 저장 → 묶음 뒤에 본 기록도 재실행 없이 같은 지도에 놓음 (in_run:false)
근사임을 화면이 말한다 t-SNE/UMAP 은 새 기록을 재실행 없이 못 놓고 numpy 를 요구해 기각, 완전 MDS 는 800² 고유값 문제라 순수 Python 에 부적합 (SL-MAP-4). 클러스터는 색이 아닌 윤곽선과 번호로 구분하고, 라벨 ●/미라벨 ○로 표시합니다 (DUMP-CLU-8).

  • run_id 고정 — 일괄 라벨은 화면이 본 그 묶음 결과에만 적용. 그새 다시 묶이면 422
  • All-or-nothing — 일괄 라벨은 선택을 한 번 검사하고 하나라도 어기면 아무것도 쓰지 않음
  • stale 표시 — 풀의 seq 가 묶음 때보다 커지면 「새 기록 있음」 (자동 재계산 안 함: 번호가 슬그머니 바뀌지 않게)

  • 다시 묶기는 백그라운드 스레드 1개 (세트당). 두 번째 요청은 돌고 있는 잡을 그대로 반환

  • DB 는 psycopg 풀, 마이그레이션은 advisory lock

10설계 결정과 기각한 대안

기각한 대안은 커밋 이력에 남지 않으므로 이 목록이 유일한 기록에 가깝습니다. 원문은 SPEC.md 의 SL-X-* 와 영역별 __spec__.md.

SL-X-1fleet 안에 분석을 넣지 않고 별도 프로젝트로
이유: fleet 은 "가져오고 해석하고 서빙"하는 곳인데, 분석이 들어오면 첫 연산·첫 파생 저장 데이터가 생긴다. 사용자가 별도 프로젝트로 분기하자고 결정. 대가: HTTP 한 단계와 캐시 전제가 생김.
SL-X-2특징 계산을 브라우저에서 하지 않는다
특징 정의가 TypeScript 에 박히고, 브라우저 없이 평가·제안이 불가능하며, 라벨이 수천 개가 되면 옮길 양이 커진다. 서버가 특징을 계산해 저장한다.
SL-X-3분류기(SVM/RF/CNN) 대신 최근접 비교
라벨 수십 개에서는 과적합만 한다. 최근접 비교는 첫 라벨부터 동작하고 근거(닮은 기록)를 그대로 보여 줄 수 있다. 클래스당 수백 라벨이 되면 재검토.
SL-X-4 · SL-TREE-2자유 태그 대신 고정 트리 + 필요 시 추가
자유 텍스트는 같은 모양을 edge drop/엣지드롭 처럼 철자별로 쪼개 제안도 같이 쪼개진다. "정해진 걸 먼저 쓰고, 없으면 그 단계에 추가". 3단계는 고정 — ID-0603 의 IFM-MIOB 같은 접두어 묶음은 4단계로 늘리지 않고 소분류 이름 안에 둔다 (SL-TREE-11: 4단계는 노드당 표본을 더 얇게 하고 단계별 평가의 의미를 깨뜨림).
SL-X-5 · SL-X-6pgvector · numpy 도입 보류
수십~수천 건을 파이썬으로 전수 비교해도 수십 ms. 폐쇄망 PG 에 확장을 하나 더 얹지 않는다. 묶기에서도 math.sumprod 로 800건 60초→6초가 나와 numpy 없이 간다. 바뀔 파일은 shape.py 하나뿐.
SL-X-7묶음을 저장하지 않고 즉석 계산하지 않는다
기록이 들어올 때마다 묶음 번호가 목록·상세·일괄 라벨 사이에서 어긋난다. 일괄 라벨은 사람이 본 구성원과 정확히 같아야 하므로 결과를 저장하고 run_id 로 못 박는다.
SL-X-8 · SL-X-9k-means · 계층 · 단일 연결 클러스터링 기각
k-means 는 k 와 상관이 아닌 벡터 공간을 요구, 평균 연결은 순수 파이썬에서 O(n³) 이고 모두가 닮는 대표가 없다. 단일 연결은 A~B~C 로 사슬이 이어진다. → 대표 시드 방식.
SL-CLU-8다시 묶기는 202 + 백그라운드 스레드
요청 하나에 매달리게 했더니 2,400건 18초에서 Next 프록시가 연결을 끊고 화면이 fleet 의 "set 다운로드 실패 — 전체 롤백됨"을 빌려 써서 500 으로 보였다. 프록시 타임아웃을 늘리는 방법은 n² 가 커지면 다른 곳에서 또 터지므로 기각. 이 일로 core/api.ts 가 fleet 의 오류 문구를 다른 상류에 빌려주지 않게 바뀌었다.
SL-ARCH-4구조화는 파일 이동만, 호환 shim 없음
테이블·컬럼·마이그레이션 체크섬이 그대로라 기존 DB 는 아무것도 할 필요가 없다. 옛 모듈 경로를 되살리는 re-export 는 낡은 호출자를 숨기므로 두지 않고, 호출자(워크스페이스 실행 구성·문서)를 같이 고쳤다. 진입점: scanlabel.application.api:app · .application.jobs · .data.migrate.
